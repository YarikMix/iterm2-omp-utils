# iterm2-utils: интеграция только с omp

Статус: одобрен пользователем 2026-11-16, включая отказ от точной проверки версии агента.

## Намерение и согласованный объём

Заменить поддержку Codex/Claude в существующем `iterm2-utils` полноценной интеграцией с omp. Причина: запуск Codex ломается после обновления из-за точного сравнения версии; пользователь переходит на omp, а не просит поддерживать несколько агентов.

Согласовано: новые сессии с поручением, восстановление диалогов, статусы, уведомления; переделка существующих навыков и установщика. Codex/Claude больше не поддерживаемые потребители или цели запуска. Удаляем их активные проверки, hooks, настройки, wrappers, команды и инструкции. При миграции убираем только принадлежащие пакету изменения; личные файлы и чужие значения не удаляем целиком.

Это переработка продукта, а не замена слова в трёх навыках. Реализация начинается только после одобрения этого документа.

## Подходы

1. **Выбрано пользователем: заменить Codex/Claude на omp внутри iterm2-utils.** Сохраняем общий транспорт iTerm2 и транзакционный установщик; удаляем многопотребительскую модель из активного продукта.
2. Добавить omp третьим потребителем: сохраняет старую сложность и проверки. Пользователь явно отверг этот смысл «переделки».
3. Отдельная интеграция в omp-utils: изолирует новую реализацию, но дублирует/переносит общий механизм. Пользователь выбрал существующий iterm2-utils.

Ни параллельная поддержка, ни алиасы `launch-codex -> launch-omp` не нужны.

## Цели, ограничения и нецели

- macOS + zsh, Python 3.11+, официальный Python SDK iTerm2; сохраняем публичность пакета и отсутствие зависимости от авторского workspace.
- Не блокируем обновление агента только из-за отличающейся строки версии. Версии фиксируем как проверенные факты, а не единственно разрешённые значения.
- Проверяем необходимые для конкретной операции CLI/API-возможности; неподдержанная функция блокирует себя, не открытие обычного shell и не независимые функции.
- Сохраняем модель, endpoint, credentials, approval mode и профиль omp. Не добавляем `--auto-approve`, не меняем защиты.
- Не создаём второй движок статусов/уведомлений, не меняем исходники omp, не переносим историю Codex/Claude в omp, не запускаем агента для preflight.
- Не закрываем и не перезапускаем существующие пользовательские вкладки; не отправляем команды в уже работающий агент.
- Приватные пути, имена проектов, prompt, экран, полный argv и настройки не входят в публичную диагностику.

## Архитектура и CLI

Сохраняем `CLI -> discovery -> pure builders -> lifecycle -> transaction engine/receipts`. Сохраняем CAS, журналы, восстановление после неизвестного результата, сравнение owned values, профили и SDK-транспорт создания вкладки.

Активная модель — один потребитель omp. У `plan/install/bootstrap-skill` больше нет выбора Codex/Claude/both; выбор функций остаётся явным. Профиль omp и профиль iTerm2 — разные сущности с разными аргументами и полями результата. Разрешение omp agent directory переиспользуем из существующей работы `omp-bootstrap`, не переписываем вторую конвенцию.

Новая команда `launch-omp` поддерживает три взаимоисключающих режима: пустая новая сессия omp, новая задача из handoff, восстановление сохранённой сессии. Обычная shell-вкладка — отдельный режим навыка, без запуска omp, проверки его версии и создания handoff. Точное именование остальных CLI-флагов — решение исполнителя; старые Codex-команды удаляются, без совместимых alias.

Профиль omp разрешаем с учётом `OMP_PROFILE`, затем `PI_PROFILE`, правил `PI_CONFIG_DIR` и default-only `PI_CODING_AGENT_DIR`; явный выбор имеет приоритет. Сохраняем выбранный профиль при запуске, поиске истории, установке extensions/MCP и подтверждении результата. Для другого профиля не используем историю/default settings молча.

## Запуск и восстановление

### Общий транспорт

- Один выбранный Python с абсолютным `sys.executable`; не подменять virtualenv базовым интерпретатором. Проверить SDK и доступ к API без автоматической установки.
- Выбор окна: явная цель; иначе согласованная привязка родительской сессии; иначе единственное окно полного валидного инвентаря. Не выбирать по фокусу/названию. Перепроверить перед созданием.
- Использовать официальный SDK с командой при создании вкладки, не terminal send/run. Одно создание на одну разрешённую вкладку; нет автоматического повторения после timeout/unknown. Несколько вкладок — только по явной просьбе с индивидуальными результатами.
- Для обычной shell-вкладки использовать обычный shell-профиль без команды агента. Для omp — выделенный профиль с наследованием выбранного родителя, без startup-команды Codex/Claude.
- Если iTerm2 возвращает только basename вместо абсолютного `argv[0]`, проверка принимает его лишь при точном совпадении остальных аргументов и независимом подтверждении ожидаемого исполняемого файла для того же foreground job в TTY созданной вкладки. Без подтверждения запуск остаётся непроверенным.
- Ограниченные ожидания: каждая внешняя операция до 10 секунд, создание и проверка запуска совместно до 30 секунд. Подтверждение получения handoff отдельно до 120 секунд.

### Гарантированно новая сессия

Обычный `omp --cwd DIR -- PROMPT` недостаточен: настройка `autoResume` может продолжить старую беседу. Пакет поставляет приватный launch overlay с единственным значением `autoResume: false`; передаёт его последним среди `--config` в новой пустой и handoff-сессии. Постоянные настройки не меняются; стандартное размещение истории сохраняется.

Смысл argv: `omp [сохранённые допустимые параметры профиля] --cwd ABS --config OWNED_OVERLAY -- HANDOFF_PROMPT`. Для пустой новой сессии нет prompt. Shell-функции нельзя бездумно обходить или исполнять для introspection: выбрать проверенный executable/понятный passthrough, сохранить существенные параметры; непрозрачный wrapper требует явного способа запуска, а не догадки.

Handoff — уникальный приватный файл с nonce и отдельным отсутствующим до запуска ack. Prompt поручает прочитать файл и записать подтверждение с идентификатором фактической сессии. Свежий валидный ack доказывает получение поручения, а не выполнение задачи. Успешное создание вкладки или identity-событие не подменяют ack.

### Resume

Используем `omp --cwd ABS --resume ABS_SESSION_FILE`, не title, prefix, latest/picker и не `--restore`. Последний продолжает прерванную работу и не равнозначен открытию истории.

До запуска проверяем существование файла, заголовок с ожидаемым ID, профиль и cwd; не выводим переписку. Отсутствие/подмена истории не превращается в новую сессию. Открытый тот же диалог — сообщить существующую вкладку; дубликат только по явному запросу.

omp может последовать `continuationOf` в следующий файл той же беседы. После запуска принимаем исходный ID либо подтверждённую цепочку continuation к нему; произвольный другой ID/fork не считается успехом. Фактический новый файл обновляет реестр. Проверка касается логического диалога, а не неизменности имени JSONL.

### Identity bridge и доказательства

Небольшое принадлежащее пакету extension публикует только идентичность основной TUI-сессии: ID, фактический session file, cwd, профиль и привязку терминала. Использует `ctx.sessionManager`, события `session_start`, `session_switch`, `session_branch`, `session_shutdown`; не создаёт статусов или уведомлений. Не работает для subagents/print/headless.

Публикация через адресованный приватный реестр и iTerm user variables; мосту не нужен отдельный daemon. Данные на диске приватны, stdout диагностика ограничена. Проверяем происхождение, session/tab/window ID и свежесть регистрации; stale запись после crash/SIGKILL сама по себе не доказывает открытый диалог. Определение живости и атомарный формат записей остаются исполнителю, но обязаны учитывать повторное использование PID, смену диалога в той же вкладке и устаревшее окружение. Не действовать на active-tab fallback. Получатель управляющих последовательностей всегда собственный tty процесса.

Результаты различают: `blocked` до создания, `created_unverified`, `unknown`, `launched`. Сохраняем известные terminal/tab/window ID при неопределённости. `launched` требует точной вкладки/профиля, процесса и полного допустимого argv; отдельно подтверждаем фактическую identity. Для handoff отдельно `ack`; для resume отдельно соответствие фактической истории/continuation. Если этого нет, явно «команда resume запущена, восстановление истории не подтверждено». Не раскрывать raw argv или экран.

## Функции установки

Все функции остаются выборочными. Перенос существующего выбора не означает включить все возможности. Для новой установки bootstrap копирует только навыки.

| Функция | Решение для omp |
| --- | --- |
| status | Переиспользовать native OSC 7501 (`idle/working/blocked/done/error`), настройку `terminal.programStatus`; никаких Codex/Claude hooks и вторых lifecycle callbacks. |
| notifications | Переиспользовать native OSC 9 для iTerm2 и настройки `completion.notify`/`error.notify`; по умолчанию штатная политика omp, включение error-уведомлений — явный выбор. Не ставить terminal-notifier/новый daemon. |
| restore | Native exact-file resume и native picker; удалить Codex restorer, fzf-зависимость и shell-dispatcher. |
| clipboard | Терминальное выделение и штатный Cmd+C; управлять только явно выбранным iTerm `CopySelection`. Не выдумывать omp `copy_on_select`, не перенаправлять Cmd+C в Ctrl+C: у omp это clear/cancel. |
| shortcuts | Сохранить выборочную настройку, но по семантике omp: Ctrl+V image paste штатный; RU-нормализация только при необходимости; Alt+Enter -> native newline/Ctrl+J; resume -> native `app.session.resume`. Ctrl+Q оставить штатному follow-up/approval, старый double-Ctrl+C удалить. Не обещать прежнюю Ctrl+C/RU copy-семантику без live-подтверждения. |
| MCP | Выборочная запись одного owned server в `mcpServers` активного omp `mcp.json`; сохранить остальные servers и root keys, отказ при foreign collision; сохранить ограниченный observe-интерфейс. |
| shell | Штатная интеграция iTerm2 и zsh, без intercept `codex`, restore aliases, model/approval overrides. |
| appearance | Сохранить правила, иконки, обычный cd/reset, TTY-проверку и APS/light/dark-защиты. Связь с основной сессией — omp identity; не ориентироваться на jobName Codex. |
| project-launcher | Сохранить shell-кнопки проектов, приватный JSON, стабильные GUID, guards ссылок. Кнопки по-прежнему открывают shell; запуск omp — отдельная явная операция. |

Выбранные native settings устанавливаем узко с receipt/CAS; значения и keybindings пользователя сохраняем вне явно выбранного изменения. Существующая эквивалентная чужая интеграция может переиспользоваться без присвоения ownership; не включаем дубликат. Сочетания выше — предложенная omp-native политика, не обещание совместимости с прежними Codex сочетаниями.

Поддержка native OSC со стороны установленного iTerm2 и реальные баннеры пока не проверены. Ошибка capability/probe сообщает feature-specific `blocked/pending`, не вызывает слепой fallback на hooks. Для project-launcher также проверяем нужную native схему вместо слепого равенства версии iTerm2.

## Миграция установленной интеграции

Отдельная операция миграции с preview до изменения; она входит в новый установщик. Новая установка без legacy receipts не проходит старые агентные проверки. Миграция не требует установленных Codex/Claude и никогда их не запускает.

1. Прочитать и проверить legacy feature receipt, все три независимых skill receipts и журналы. Сначала восстановить незавершённые транзакции по их исходной семантике. Исторические decoder/адресные форматы — совместимость данных миграции, не поддержка старых агентов в новом продукте.
2. Показать только план owned ресурсов: что переносится, снимается, сохраняется из-за конфликта. Нет receipt — нет права удалить по имени или похожему пути. Секреты и полные config bodies не печатать.
3. Общие пригодные неизменённые ресурсы appearance/launcher/shell переносить ownership-операцией, сохраняя исходные `before` и GUID, а не удалять и создавать заново. Omp профили не наследуют ошибочные агентные keybindings.
4. Удалить/вернуть прежние значения только по точным owned адресам и при совпадении с installed: отдельные hooks, JSON/TOML settings, MCP registration, именованные zsh-блоки, owned профили, файлы навыков. Не удалять директории/history/config целиком. Старые MCP записи очищать адресно без агентного CLI; если происхождение/формат не доказаны — отчёт о конфликте, а не догадка.
5. Особый случай — до установки пакета существовала внешняя интеграция, которую пакет отключил. Не восстанавливать её молча: preview отдельно показывает возможную реактивацию Codex/Claude. Предложение дизайна — оставить её отключённой; это явное решение миграции с сохранением исходного состояния в журнале, не обычный inverse uninstall. Пользователь может выбрать восстановление внешнего значения в preview.
6. Изменённые пользователем owned-ресурсы не затирать. Сохранять retryable legacy-cleanup state независимо от новой omp selection; результат не «полностью очищено», пока остаются конфликты. Независимые omp функции могут устанавливаться, но конфликтующий ресурс не перезаписывается и дубликаты writers не создаются.
7. Не удалять profile GUID, на которые ссылаются live/buried sessions, default/surviving profiles или неполный inventory. Не закрывать сессии. Для выполняющихся старых shell сохранять необходимый прежний immutable runtime до безопасной явной очистки; он не поставляется и не активируется новой установкой. Отчёт отличает persisted cutover от старых уже запущенных процессов.
   - Для очистки исторического `current` и его релизов требуется отдельный успешный снимок сессий напрямую из официального SDK iTerm2. Снимок включает сессии в окнах, свёрнутые панели и скрытые (`buried`) сессии. Успешный полный пустой снимок — необходимое, но не достаточное условие: сохраняются доказательство отсутствия сохранённых ссылок, проверка исходных значений и повторная проверка под блокировками. При ошибке, неполном снимке или любой сессии очистка откладывается. Preview использует тот же read-only запрос, что и apply, без запуска агента и без создания окна или вкладки.
   - Формат status bar, настройка её позиции и профили не нужны этому снимку. Для операций над профилями и статус-баром сохраняется отдельная строгая проверка. Путь активного runtime остаётся `current`; новый стабильный указатель не вводим. Тесты проверяют пустой снимок при несовместимой схеме статус-бара, отказ при неполном ответе и защиту при live/minimized/buried сессии или сохранённой ссылке.
8. Старые owned копии трёх навыков в Codex/Claude убирать по собственным receipts; чужие/изменённые файлы оставлять как конфликт. Новые bundles устанавливать только в выбранный omp profile. Existing `omp-bootstrap` использовать с уважением к незавершённой работе, не перезаписывать чужие изменения.

В активной CLI/документации/пакете после cutover нет Codex/Claude consumer code. Ограниченный reader/recovery legacy state допускается только для завершаемой миграции; он не делает discovery версий, preflight или launch старых агентов. Не разрешать «remove legacy support» уничтожить возможность безопасно обработать существующий journal.

## Навыки и документация

- `iterm2-launch`: ordinary shell, new omp, handoff, exact resume; не предлагать/запускать Codex. Явно отделять tab creation, agent launch, identity/history и receipt поручения. Не требовать sandbox metadata, которых нет у omp host; обычные разрешения среды и запреты UI сохраняются.
- `iterm2-setup`: один агент omp, выбор функций, preview/install/migrate/update/uninstall/doctor и честная live-проверка.
- `iterm2-projects`: прежний shell launcher с omp ownership и без выбора Codex/Claude.
- Обновить README, AGENTS.md, changelog, feature/compatibility docs, dependency notices/lock/export allowlists и validators. Старые design/validation документы оставить историческими, не выдавать результаты Codex за проверку omp.

## Проверка и приёмка

Автоматическая проверка только с TemporaryDirectory HOME и fake adapters: не читать реальные auth/settings для fixture tests. Сохранить generic CAS/journal/rollback/foreign-resource/native-reference coverage. Убрать obsolete active-agent suites; исторические данные оставить migration fixtures.

Проверяемые сценарии:

- новое поручение при глобальном/project `autoResume:true` создаёт новый ID, прежний диалог не меняется, постоянный config не меняется;
- named omp profile сохраняет настройки/размещение истории; корректные пробелы и quoting cwd/handoff;
- одна созданная вкладка при успехе, timeout/unknown не вызывают вторую; wrong window/profile/argv не дают `launched`;
- exact resume, continuation, подменённый заголовок, missing file, открытый/устаревший registry; нет fallback в fresh;
- main-only identity: start/switch/branch, undefined file, crash/stale, shutdown; ack nonce/freshness и отдельные статусы доказательств;
- старые receipts/журналы/skill receipts, bare/pair owners, changed values, отсутствующие Codex/Claude, прежние adopted hooks, referenced profiles, повторный cleanup и сохранение чужих значений;
- native настройки меняются только по выбранным адресам, MCP/keybindings не уничтожают соседние entries; никакого двойного статуса/уведомления.

После реализации — обязательные repository unittest и skill/export checks один раз на итоговом изменении. CLI smoke в временном HOME. Live-проверки требуют разрешённой установки выбранных функций и создания собственных тестовых вкладок: shell; новая omp/ack; resume/history; native working/blocked/done/error; один banner; EN/RU clipboard/paste/newline и сохранение Ctrl+Q; cd/reset/appearance и project buttons. Не симулировать итоговый success подменой пользовательских экранов или продакшен-настроек. Если разрешения/API/receiver недоступны, указать конкретный непроверенный сценарий; fixtures не считаются live acceptance.

## Основания и границы уверенности

Исследован установленный omp 18.20.2; `omp --help` выполнен, сессии не запускались. Публичный source установленного `@oh-my-pi/pi-coding-agent`: `main.ts` (session selection/continuation), `modes/settings.ts` и `config/settings.ts` (autoResume/overlays), `utils/run-status.ts` (OSC 7501), `utils/title-generator.ts` (identity только для Tern), `extensibility/shared-events.ts`, `extensions/types.ts`, `session/session-manager.ts`, `mcp/config-writer.ts`; `@oh-my-pi/pi-tui` — keybindings и iTerm OSC 9.

В iterm2-utils исследованы `launch_checks.py` (точный Codex pin), `launch_api.py`, `engine.py`, `state.py`, `lifecycle.py`, feature builders и отдельные skill receipts. Существующий `docs/superpowers/specs/2026-11-16-omp-bootstrap-design.md` относится лишь к hosting навыков; этот дизайн заменяет его ограничения там, где они мешают omp-only cutover.

Решения исполнителя: внутренние имена модулей, точный CLI spelling кроме `launch-omp`, атомарный приватный registry, способ narrow YAML edits с сохранением соседних значений, группировка транзакционных checkpoints и тестовых fixtures. Они не могут ослаблять описанные гарантии или возвращать активную поддержку Codex/Claude.
